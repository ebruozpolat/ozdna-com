fallback is compiling Meta's reference C++ to WASM ourselves") and ledger item **C1**.

## Question

Can we get Meta's reference **PDQ** (256-bit perceptual hash, the §1.5 confirmation stage)
into the browser and Cloudflare Workers via the npm `pdq-wasm` package — or do we fall back
to compiling Meta's C++ to WASM ourselves?

## Result: **spike PASSES** — adopt `pdq-wasm@0.3.9`, vendor the binary.

Verified locally (Node 22, clean `npm install pdq-wasm@0.3.9`):

- `PDQ.hash({data,width,height,channels})` returns a **32-byte (256-bit)** hash + a
  `quality` 0–100 score. ✅
- `toHex` → **64 lowercase hex**; `fromHex` round-trips with **distance 0**. ✅
- **Deterministic** (same pixels → identical hash). ✅
- `hammingDistance` behaves: self = 0, bit-opposite = 256, near-duplicate ≪ unrelated image
  (structured gradient vs. a ±2-noise copy = 36; vs. a different image = 105). ✅
- `areSimilar(threshold = 31)` matches our §1.5 confirmation threshold. ✅
- Package ships a **prebuilt `wasm/pdq.wasm` (25.9 KB)** — no local toolchain build needed.
- BSD-3-Clause. Redistribution (vendoring) permitted.

So the C++-compile fallback is **not needed for v1**. It stays documented as the escape hatch
if the single-maintainer package goes unmaintained.

## Caveats found (these shape the integration — read before wiring `apps/*`)

1. **The ESM Node auto-loader is broken.** `import { PDQ } from 'pdq-wasm'` then `PDQ.init()`
   in an ESM Node context throws `PDQ WASM module not available … run build:wasm`
   (`getWasmFactory()` returns null). The **CommonJS `require` path works**; the ESM path
   does not resolve the bundled factory. Our monorepo is `"type": "module"`, so we do **not**
   rely on the auto Node path — we pass the wasm explicitly (below).
2. **Cloudflare Workers needs manual instantiation.** Workers is ESM and has **no `document`**,
   so neither the package's Node loader (`fs.readFileSync`) nor its browser loader
   (`<script>` + `document.head`) applies. For `apps/api` metered server-side compute we
   instantiate the Emscripten factory from the imported `pdq.wasm` binary ourselves
   (`import wasm from '../../vendor/pdq-wasm/wasm/pdq.wasm'` → `createPDQModule({ wasmBinary })`).
3. **Single maintainer, no release since Nov 2025** (as §1.4 warned). Mitigated by vendoring
   the exact binary we tested (pinned + SHA-256'd) so upstream changes/unpublish can't move us.
4. **Quality score matters.** Near-flat images get a low `quality`; §1.3/§1.5 already say pHash
   is unreliable there. Persist `quality` and refuse to treat a low-quality PDQ as a
   confirmation (wire when `apps/*` scoring lands).

## What shipped this slice (dna-core — the pure, canonical half)

- `packages/dna-core/src/pdq.ts` — **no wasm dependency** (same discipline as anchor-backends
  keeping viem out of the shared layer): `pdqDistance` (256-bit Hamming, popcount table),
  `pdqConfirms` / `PDQ_CONFIRM_MAX = 31`, `pdq256ToHex` / `pdq256FromHex` (validated), `scorePdq`,
  and the **`PdqHasher` contract** the platform injects. 15 tests, incl. a lockstep assertion
  that `PDQ_CONFIRM_MAX === verdict.THRESHOLDS.pdqConfirm`.
- `vendor/pdq-wasm/` — the prebuilt `pdq.wasm` + glue + LICENSE + provenance/integrity README.
- The **hash producer is deliberately NOT reimplemented in TypeScript.** PDQ's whole value is
  being the industry-standard hash; a non-bit-exact JS clone would break cross-tool interop and
  could silently diverge. Distance/encoding are unambiguous and safe to own; the hash is not.
